# ClickPop — معماری کلان (Step 1)

سند مرجع معماری برای پلتفرم **کلیک‌پاپ / ClickPop** (`clickpop.ir`) — تم سفارشی وردپرس + افزونهٔ اختصاصی «ClickPop Core Engine».

> نسخهٔ سند: `1.0` · وضعیت: پیش‌نویس معماری، قبل از تولید کد · دامنهٔ هدف: `clickpop.ir`

---

## ۱. فرضیات صریح (Explicit Assumptions)

این فرضیات تا زمان تأیید یا اصلاح، مبنای طراحی هستند. هر تغییر در آن‌ها بخش‌های علامت‌خوردهٔ سند را تحت تأثیر قرار می‌دهد.

| # | فرضیه | تأثیر بر معماری |
|---|---|---|
| A1 | PHP `8.2+` (توسعه روی 8.3)، WordPress `6.5+`، MySQL `8.0` / MariaDB `10.6+` با موتور InnoDB | استفاده از `readonly`, `enum`, `never`, named args, و `SELECT … FOR UPDATE` |
| A2 | میزبانی VPS با Nginx + PHP-FPM + OPcache + **Redis** (Object Cache) | لایهٔ کش مبتنی بر `wp_cache_*` با گروه اختصاصی، نه صرفاً transient |
| A3 | تأمین‌کنندهٔ اولیه: **followeran.ir** (`https://my.followeran.ir/api/v2`) — سازگار با SMM Panel API v2 | درایور `FollowerAnProvider` + درایور عمومی `SmmPanelV2Provider` |
| A4 | فیلد `rate` در پاسخ `action=services` قیمت **به ازای ۱۰۰۰ واحد** و به **تومان (IRT)** است | فرمول قیمت‌گذاری `unit_cost = rate / 1000` — **نیاز به تأیید (Q3)** |
| A5 | واحد پول داخلی: **ریال** برای ذخیره‌سازی (BIGINT)، **تومان** برای نمایش | حذف کامل float از مسیر پول |
| A6 | ورود کاربر با **شمارهٔ موبایل + OTP** به‌عنوان مسیر اصلی، رمز عبور به‌عنوان مسیر جایگزین | ماژول `Auth` با درایور SMS |
| A7 | زبان پیش‌فرض فارسی (RTL)؛ en/ru/zh در فاز دوم با Polylang | همهٔ رشته‌ها از روز اول i18n-شده |
| A8 | حجم بار هدف: ~۵۰ سفارش/دقیقه در پیک، ~۲۰۰ کاربر همزمان | جداول اختصاصی + ایندکس ترکیبی، نه CPT برای سفارش |
| A9 | Elementor Free + Pro نصب است؛ اما سایت **بدون** Elementor هم باید بالا بیاید (degrade) | ثبت ویجت‌ها پشت گارد `did_action('elementor/loaded')` |
| A10 | افزونهٔ سئو خارجی (Rank Math / Yoast) ممکن است نصب شود | ماژول سئوی تم خودش را در حضور آن‌ها غیرفعال می‌کند |

## ۲. تصمیم‌های معماری کلیدی (ADR خلاصه)

### ADR-01 — جداسازی سخت تم و افزونه
تم **فقط ارائه** (presentation) است. هیچ منطق تجاری، هیچ کوئری مستقیم به جداول `cp_*`، هیچ تماس API در تم وجود ندارد.
افزونه یک **API داخلی پایدار** (`ClickPop\Core\Api\Facade` + REST) بیرون می‌دهد که تم مصرف می‌کند. نتیجه: تعویض تم بدون از دست رفتن داده، و اجرای افزونه روی هر تم دیگری.

### ADR-02 — جداول اختصاصی به‌جای Custom Post Type
سفارش‌ها، تراکنش‌ها، سرویس‌ها و تیکت‌ها در جداول `{$wpdb->prefix}cp_*` ذخیره می‌شوند، نه `wp_posts`/`wp_postmeta`.
**دلیل:** الگوی کوئری این داده‌ها (فیلتر روی status + user_id + بازهٔ زمانی، مرتب‌سازی، شمارش) با `meta_query` به‌شدت کند می‌شود؛ ۱۰۰هزار سفارش یعنی ۱M+ ردیف postmeta. ایندکس ترکیبی روی جدول اختصاصی، کوئری را از ~۸۰۰ms به <۵ms می‌رساند.
**استثنا:** *صفحات فرود سرویس* (محتوای سئویی و قابل ویرایش با المنتور) یک CPT به نام `cp_service_page` هستند که با `service_id` به ردیف `cp_services` گره می‌خورند. یعنی: **دادهٔ تراکنشی در جدول، محتوای سئویی در CPT.**

### ADR-03 — پول به‌صورت عدد صحیح ریال
هر مبلغ `BIGINT UNSIGNED` بر حسب **ریال** است. هیچ `FLOAT`/`DOUBLE` در مسیر پول نیست. یک Value Object به نام `Money` تنها راه ساخت/جمع/تقسیم مبلغ است.
**دلیل:** `0.1 + 0.2 !== 0.3` در float؛ در سیستم کیف پول این یعنی مغایرت تراز.

### ADR-04 — دفتر کل فقط-افزودنی (Append-only Ledger)
`cp_transactions` هرگز UPDATE یا DELETE نمی‌شود. موجودی کیف پول (`cp_wallets.balance`) یک **ماده‌سازی (materialized) کششده** از دفتر کل است. هر ردیف `balance_after` را ثبت می‌کند تا مغایرت‌گیری (reconciliation) ممکن باشد.
یک کرون شبانه `SUM(signed_amount)` را با `cp_wallets.balance` مقایسه می‌کند و مغایرت را alert می‌زند.

### ADR-05 — تراکنش دیتابیس هرگز روی I/O شبکه باز نمی‌ماند
جریان ثبت سفارش به دو فاز شکسته می‌شود (Saga): فاز رزرو پول (اتمیک، داخل تراکنش، بدون شبکه) و فاز فراخوانی تأمین‌کننده (خارج تراکنش). سفارش‌های یتیم با کرون آشتی‌دهنده (reconciler) پاک‌سازی می‌شوند.
**دلیل:** یک تایم‌اوت ۱۵ ثانیه‌ای در API تأمین‌کننده نباید ردیف کیف پول را ۱۵ ثانیه قفل کند.

### ADR-06 — REST-only، بدون `admin-ajax.php`
تمام ارتباط فرانت با `wp-json/clickpop/v1/*`. `admin-ajax` فقط برای صفحات ادمین قدیمی نگه داشته می‌شود.
**دلیل:** `admin-ajax` کل `admin.php` را بوت می‌کند (~۴۰ms اضافه)، cache-friendly نیست و `permission_callback` استاندارد ندارد.

### ADR-07 — یک شیت CSS برای RTL و LTR
هیچ `rtl.css` جداگانه‌ای وجود ندارد. تمام فاصله‌گذاری و موقعیت‌دهی با **Logical Properties** نوشته می‌شود (`margin-inline-start`, `padding-block`, `inset-inline-end`, `border-start-start-radius`).
**دلیل:** حذف ~۴۰٪ حجم CSS تکراری و حذف کل کلاس خطای «راست‌چین شد ولی این یکی نه».

### ADR-08 — دارک‌مود بدون فلیکر با اسکریپت مسدودکنندهٔ ریز
یک اسکریپت inline زیر ۳۰۰ بایت در `<head>` (قبل از هر CSS) `localStorage` را می‌خواند و `data-theme` را روی `<html>` می‌گذارد. تمام رنگ‌ها CSS Custom Property هستند.
**دلیل:** هر راهکار مبتنی بر `DOMContentLoaded` یک فریم سفید (FOUC) می‌دهد.

## ۵. جریان‌های حیاتی

### ۵.۱ ثبت سفارش (Saga دو-فازی)

```
کاربر                REST              Orders           Wallet           Provider
 │  POST /orders      │                  │                │                 │
 ├───────────────────►│                  │                │                 │
 │                    │ nonce+cap+rate   │                │                 │
 │                    │ limit check      │                │                 │
 │                    ├─────────────────►│                │                 │
 │                    │                  │ ۱. سرویس فعال؟ min/max؟ لینک معتبر؟
 │                    │                  │ ۲. قیمت *سمت سرور* محاسبه شود      │
 │                    │                  │    (قیمت ارسالی کلاینت دور ریخته می‌شود)
 │                    │                  │ ۳. idempotency_key بررسی شود       │
 │                    │                  ├───────────────►│                 │
 │                    │                  │  BEGIN TRANSACTION               │
 │                    │                  │  UPDATE cp_wallets SET balance=balance-X
 │                    │                  │    WHERE user_id=? AND balance>=X │
 │                    │                  │  affected_rows=0 → موجودی ناکافی  │
 │                    │                  │  INSERT cp_transactions (order, -X)
 │                    │                  │  INSERT cp_orders status='reserved'
 │                    │                  │  COMMIT      ← هیچ شبکه‌ای اینجا نیست
 │                    │                  │◄───────────────┤                 │
 │                    │                  │ ۴. action=add  │                 │
 │                    │                  ├────────────────┼────────────────►│
 │                    │                  │                │   timeout 15s   │
 │                    │                  │◄───────────────┼─────────────────┤
 │                    │                  │ موفق → remote_order_id، status='processing'
 │                    │                  │ خطای تجاری → بازگشت وجه، status='failed'
 │                    │                  │ تایم‌اوت/شبکه → status='pending_verify'
 │                    │                  │                → کرون آشتی‌دهنده تعیین تکلیف می‌کند
 │◄───────────────────┤                  │                │                 │
```

**نکات ضدخطا:**
- `idempotency_key` (UUID تولیدشده در کلاینت) `UNIQUE` است ⇒ دابل-کلیک سفارش تکراری نمی‌سازد.
- خطای شبکه ≠ خطای تجاری. در خطای شبکه **هرگز** به‌صورت خودکار بازگشت وجه نمی‌دهیم (ممکن است سفارش ثبت شده باشد)؛ به `pending_verify` می‌رود و reconciler با `action=status` تعیین تکلیف می‌کند.
- برداشت با `UPDATE … WHERE balance >= X` انجام می‌شود، نه `SELECT` سپس `UPDATE` — این الگو race condition ندارد و به قفل صریح نیاز ندارد.

### ۵.۲ همگام‌سازی وضعیت سفارش‌ها

Action Scheduler هر ۵ دقیقه: انتخاب حداکثر ۱۰۰ سفارش `processing` با `synced_at < NOW() - INTERVAL 5 MINUTE` → یک فراخوان `action=status` با `order=1,2,3,…` → به‌روزرسانی دسته‌ای.
نگاشت وضعیت‌ها و سیاست بازگشت وجه در `docs/03-API-CONTRACT.md`.
Backoff تطبیقی: سفارش تازه هر ۵ دقیقه، بعد از ۶ ساعت هر ۳۰ دقیقه، بعد از ۲۴ ساعت هر ۲ ساعت.

### ۵.۳ افزایش موجودی

```
کاربر → POST /wallet/topup → ساخت cp_transactions(status='initiated', authority=null)
     → درگاه: درخواست authority → ذخیره authority (UNIQUE) → ریدایرکت
     → بازگشت کاربر (GET callback) → *هرگز به پارامترهای GET اعتماد نکن*
     → فراخوان server-to-server تأیید (verify) با مبلغ ذخیره‌شده در DB
     → قفل روی authority (UPDATE … WHERE status='initiated') → اگر affected_rows=0 یعنی
       قبلاً پردازش شده → پاسخ idempotent، بدون شارژ دوباره
     → COMMIT: موجودی + ریز تراکنش
```

### ۵.۴ همگام‌سازی سرویس‌ها

روزی ۴ بار + دکمهٔ دستی در ادمین. برای هر سرویس یک `hash` از فیلدهای معنادار محاسبه می‌شود؛ فقط ردیف‌های تغییرکرده UPDATE می‌شوند. سرویس‌های حذف‌شده از سمت تأمین‌کننده `status='archived'` می‌گیرند (**هرگز DELETE نمی‌شوند** چون سفارش‌های تاریخی به آن‌ها ارجاع دارند). افزایش قیمت بیش از آستانه (پیش‌فرض ۲۰٪) سرویس را به صف «تأیید دستی» می‌برد تا فروش زیر قیمت تمام‌شده رخ ندهد.

## ۶. موتور قیمت‌گذاری

```
provider_rate (تومان/۱۰۰۰)
   → تبدیل به ریال صحیح:  cost_per_1k = provider_rate × 10
   → اعمال نرخ ارز (اگر تأمین‌کننده ارزی باشد؛ برای followeran ضریب = ۱)
   → حل قاعدهٔ سود بر اساس اولویت:  service > category > brand > global
   → margin_type = percent | fixed
   → اعمال حداقل سود مطلق (min_profit) برای جلوگیری از سود صفر روی سرویس ارزان
   → گرد کردن به بالا (ceil) با گام قابل تنظیم (پیش‌فرض ۱۰۰۰ ریال = ۱۰۰ تومان)
   → sale_per_1k
قیمت نهایی سفارش:  charge = ceil(sale_per_1k × quantity / 1000)
```

- محاسبه **همیشه سمت سرور**. قیمت نمایشی در فرم فقط برای UX است و در `POST /orders` نادیده گرفته می‌شود.
- نتیجهٔ قیمت هر سرویس در `cp_services.sale_rate` ماده‌سازی و در Redis کش می‌شود؛ با تغییر هر قاعده، کش کل باطل و بازمحاسبه می‌شود (کرون، نه در درخواست کاربر).
- `service_rate` تأمین‌کننده (مثل `"3.110"`) معنایش نامعلوم است — تا تعیین تکلیف، خام ذخیره می‌شود و در قیمت‌گذاری استفاده نمی‌شود (**Q4**).

## ۷. ماشین حالت سفارش

```
                 ┌─────────┐
                 │ reserved│ (پول کسر شد، هنوز ارسال نشده)
                 └────┬────┘
        ┌─────────────┼──────────────┐
        ▼             ▼              ▼
  ┌──────────┐  ┌──────────────┐  ┌────────┐
  │processing│  │pending_verify│  │ failed │→ بازگشت کامل وجه
  └────┬─────┘  └──────┬───────┘  └────────┘
       │               │ (reconciler)
       │◄──────────────┘
       ▼
 ┌──────────┬──────────┬──────────┬──────────┐
 │completed │ partial  │ canceled │ refunded │
 └──────────┴────┬─────┴────┬─────┴──────────┘
                 │          │
        بازگشت نسبی      بازگشت کامل
      (بر اساس remains)
```

گذارهای مجاز در `OrderStateMachine` به‌صورت جدول ثابت تعریف می‌شوند؛ هر گذار غیرمجاز استثنا پرتاب می‌کند و در `cp_audit_log` ثبت می‌شود. بازگشت وجه **همیشه** یک ردیف جدید در دفتر کل است، نه ویرایش ردیف قبلی.

| موجودی تأمین‌کننده | transient | ۵ دقیقه | دکمهٔ ادمین |
| صفحات محتوایی | Full-page cache (Nginx/افزونه) | ۱۲ ساعت | انتشار محتوا |
| داشبورد کاربر | **کش نمی‌شود** — هدر `Cache-Control: private, no-store` | — | — |
| پاسخ REST سرویس‌ها | `Cache-Control: public, max-age=300` | ۵ دقیقه | ETag |

قانون سخت: هیچ مسیر شامل موجودی یا سفارش کاربر نباید در کش عمومی بیفتد. کوکی `cp_logged_in` سیگنال bypass کش لبه است.
